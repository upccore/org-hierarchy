# Сложность выборки и оптимизация

## Как устроен запрос сейчас

Таблица хранит дерево как список смежности: у каждой записи есть
`parent_id`. Поиск коллег делается одним запросом из двух рекурсивных CTE:

1. `ancestors` - от сотрудника вверх по `parent_id` до первого офиса.
   Это h шагов, где h - глубина сотрудника (в тестовых данных 2-3).
   Каждый шаг - поиск по первичному ключу, O(log N).
2. `descendants` - от офиса вниз по всем потомкам. Каждый шаг рекурсии
   ищет детей текущего уровня по индексу на `parent_id`. Всего это
   O(k * log N), где k - число записей в офисе (отделы + сотрудники).

Итого O((h + k) * log N): время зависит от размера одного офиса, а не от
всей таблицы. Это держится на индексе `org_unit_parent_id_idx` - без него
каждый шаг спуска читал бы всю таблицу.

`UNION` вместо `UNION ALL` нужен, чтобы запрос не зациклился, если в данных
вдруг окажется цикл. Импорт циклы и так не пропускает, так что это просто
подстраховка.

## EXPLAIN ANALYZE

План для сотрудника id=13 (Москва, вложенный отдел), PostgreSQL 10,
сокращён:

```
Sort  (actual time=0.365..0.367 rows=7 loops=1)
  CTE ancestors
    ->  Recursive Union  (rows=4 loops=1)
          ->  Index Scan using org_unit_pkey on org_unit  (rows=1 loops=1)
                Index Cond: (id = 13)
          ->  Hash Join  (rows=1 loops=4)
                ->  Seq Scan on org_unit u  (rows=19 loops=3)
  CTE descendants
    ->  Recursive Union  (rows=13 loops=1)
          ->  CTE Scan on ancestors  (rows=1 loops=1)
                Filter: (type = 1)
          ->  Hash Join  (rows=3 loops=4)
                ->  Seq Scan on org_unit u_1  (rows=19 loops=4)
  ->  CTE Scan on descendants  (rows=7 loops=1)
        Filter: (type = 3)
Execution time: 0.801 ms
```

Подъём прошёл 4 записи: сотрудник → два отдела → офис. Спуск сделал 4
итерации (`loops=4`): под офисом три уровня, а на четвёртой итерации детей
уже нет, и рекурсия останавливается. В таблице всего 19 строк, поэтому PostgreSQL выбирает `Seq Scan` -
прочитать её целиком дешевле, чем идти по индексу. На большой таблице здесь
будет `Index Scan` по `parent_id`.

Ещё одна особенность PostgreSQL 9.6/10: CTE всегда материализуется, и фильтр
`type = 3` применяется уже после того, как обойдено всё поддерево офиса.
Для этой задачи это неважно - отделы всё равно нужно обойти, чтобы найти
сотрудников.

## Как можно ускорить

Для данных такого размера текущий вариант подходит: запрос выполняется
меньше чем за миллисекунду, а схема простая. Если записей станет сотни
тысяч, я бы рассмотрел два варианта.

### Колонка office_id

У каждой записи хранить id её офиса и сделать по нему индекс. Заполнять при
импорте. Тогда поиск коллег становится обычным запросом без рекурсии:

```sql
SELECT name
FROM org_unit
WHERE office_id = (SELECT office_id FROM org_unit WHERE id = %s)
  AND type = 3;
```

Это O(log N + m), где m - число сотрудников офиса. Минус: если отдел
переезжает в другой офис, нужно обновить office_id у всего отдела. Вариант
хорош именно для этой задачи, потому что «офис» - всегда верхний уровень.

### Путь от корня (ltree)

Хранить у каждой записи путь вида `7.11.12.13` в колонке типа `ltree`
(расширение PostgreSQL) с GiST-индексом. Всё поддерево офиса достаётся одним
индексным запросом:

```sql
SELECT name FROM org_unit WHERE path <@ '7' AND type = 3;
```

Офис сотрудника - это первый элемент его пути. Минус тот же: при переносе
узла надо переписать пути у всех его потомков. Зато такой вариант подходит
не только для поиска по офису, но и для любых запросов к поддеревьям.
